# **1. 문제 정의: MyBatis… 왜 이렇게 복잡해 보이지?**

지금까지는 주로 JPA만 써왔다.  
@Entity, @Repository, @Query 정도만 알면 웬만한 CRUD 작업은 금방 만들 수 있었고,  
연관관계 매핑과 Fetch 전략만 잘 신경 쓰면 꽤 강력한 개발 경험을 누릴 수 있었다.  

그러던 중, 처음으로 MyBatis 기반의 프로젝트를 맡게 됐다.  
근데 첫인상부터 당황스러웠다.  

- XML 파일 따로 만들어야 하고  
- Mapper 인터페이스 만들어야 하고  
- resultMap이라는 것도 정의해야 하고  
- 애초에 쿼리를 내가 직접 다 작성해야 한다...?

> "이거, 그냥 쿼리 짜서 JDBC 쓰는 거랑 뭐가 다른 거지?"

JPA에 익숙했던 입장에서 MyBatis는 **너무 수동적이고 복잡해 보였다.**

<div class="space-item-3"></div>



# **2. 객체 중심 사고와의 충돌 (아.. 나 이런거 몰랐네..??)**

## ✅ 기존 JPA 경험

- 객체 모델 먼저 설계 → DB 설계와 연동  
- 변경 감지, Cascade, 영속성 전이 등 자동화된 처리  
- 쿼리를 작성하지 않아도 되는 구조  

## ❌ MyBatis 첫 사용 시 느낀 어려움

- 객체 설계보다는 **쿼리 중심 사고**가 필요  
- 쿼리를 작성하지 않으면 아무것도 안 되는 구조  
- 일일이 매핑을 해줘야 하는 번거로움  
- 여러 SQL Mapper 파일이 흩어져 있어서 구조 파악이 처음엔 어렵다

📌 정리하자면, MyBatis는  
**“자동으로 해주는 것”이 없어서 처음엔 불편하고 부담스럽다.**

<div class="space-item-3"></div>



# **3. 원인 분석: JPA는 추상화, MyBatis는 명시화**

🚀 1️⃣ JPA는 추상화 중심  
- 엔티티 설계 → 쿼리 자동 생성  
- 개발자가 신경 쓸 범위를 줄여줌  
- 하지만 복잡한 쿼리나 성능 튜닝엔 제약 발생  

🚀 2️⃣ MyBatis는 제어 중심  
- SQL을 내가 직접 짜고 매핑까지 관리  
- 복잡한 조건, 동적 SQL, 프로시저 등 자유롭게 다룰 수 있음  
- 객체보단 DB와 쿼리가 중심이 되는 사고 구조 필요  


두 프레임워크가 지향하는 방향 자체가 완전히 다르다.  
MyBatis가 불편했던 건 ‘낯설었기 때문’이지, ‘비효율적이기 때문’은 아니었다.

<div class="space-item-3"></div>



# **4. 해결 방법: MyBatis에 적응하기 위한 전략**

## 🚀 MyBatis를 이해하기 위해 취한 접근 방법:

1️⃣ XML → Mapper → 도메인 구조의 흐름을 먼저 파악  
2️⃣ resultMap, @Results 등을 활용한 매핑 방식 구조화  
3️⃣ 반복되는 쿼리 패턴에 대해 공통 Mapper 구조 정리  
4️⃣ 직접 SQL을 짜면서 쿼리 최적화까지 함께 고려하는 습관  
5️⃣ 복잡한 조회 로직은 오히려 MyBatis에서 더 단순하게 정리할 수 있다는 점에 집중


<div class="space-item-3"></div>



# **5. 기술적 인사이트: MyBatis가 유리한 상황은 따로 있다**

## ✅ **MyBatis가 특히 잘 맞는 상황**

- 레거시 DB를 활용해야 할 때  
- SQL 튜닝이 중요한 서비스  
- 복잡한 다단계 조인이나 동적 조건 처리  
- 프로시저 호출이 많은 경우  
- DB 스키마가 비정형적이거나 자주 바뀌는 경우  
- 엔티티보다 SQL 중심 사고가 필요한 시스템  

## ✅ **JPA보다 더 나은 선택이 되는 순간들**

- 객체 구조가 복잡하게 얽혀 있을 때  
- 쿼리 성능이 중요할 때  
- 쿼리 결과를 명확하게 파악하고 싶은 경우  
- “자동화된 추상화”보다 “명시적인 제어”가 중요한 경우  

<div class="space-item-3"></div>



## **6. 결론: 처음엔 어렵지만, 실무에선 꽤 강력한 무기**

처음에는 정말 복잡하고 귀찮게 느껴졌던 MyBatis.  
하지만 시간이 지나면서 이 복잡함은 **“명확함”과 “제어력”의 다른 표현**이라는 걸 알게 됐다.  

✔ JPA는 “편하고 자동적”이다.  
✔ MyBatis는 “불편하지만 명확하고 유연”하다.  

📌 실무에서는 오히려 후자가 더 중요한 순간이 많다.

<div class="space-item-3"></div>



# **7. 마치며: 프레임워크보다 중요한 건 통제 가능한 구조**

이번 경험을 통해, 대세나 신기술이 모든 정답은 아니라는 걸 다시 한 번 느꼈다.  
JPA와 MyBatis는 서로 완전히 다른 철학을 가진 도구고,  
내가 만드는 시스템의 특성과 목적에 따라 **선택 기준이 달라져야 한다.**

MyBatis는 분명 낯설지만,  
복잡한 현실 속에서는 더 날카로운 도구가 될 수 있다.


📌 결론:  
✅ **JPA는 설계 추상화와 생산성을 높이기 위한 도구**  
✅ **MyBatis는 성능 제어와 구조 명확성을 위한 도구**

📌 초반에는 익숙하지 않았지만, “내가 직접 설계하고 통제할 수 있다”는 점에서  
점점 **MyBatis가 더 투명하고 안정적**이라는 인식을 갖게 됐다.
